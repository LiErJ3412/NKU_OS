发现没有`(THU.CST) os is loading ...`输出，也就说明没有执行`kern_init`

```c
int kern_init(void) {
    extern char edata[], end[]; 
    // 这里声明的两个符号由链接器定义，分别指向.data段结束和.bss段结束
    memset(edata, 0, end - edata); 
    // 清除.bss段：由于内核没有标准库，memset需要我们自己实现

    const char *message = "(THU.CST) os is loading ...\n";
    cprintf("%s\n\n", message); // cprintf是我们在ucore中自己实现的格式化输出函数

    while (1)
        ; // 进入无限循环
}
```

也就是没有执行`lab1/kern/init/entry.S`里面的`tail kern_init`，OpenSBI并没有执行内核。

后发现是opensbi版本太高了，对于makefile中的最后一句，他只会加载到内存中，却不会自动从0x80200000之后开始执行代码。

```makefile
.PHONY: qemu 
qemu: $(UCOREIMG) $(SWAPIMG) $(SFSIMG)
#	$(V)$(QEMU) -kernel $(UCOREIMG) -nographic
	$(V)$(QEMU) \
		-machine virt \
		-nographic \
		-bios default \
		-device loader,file=$(UCOREIMG),addr=0x80200000
```

后由AI建议改为`-kernel bin/ucore.img`会自动加载默认地址0x80200000,然后自动执行，为了保持和指导书一致最终选择降级版本。

替换qemu中的opensbi为低版本，即可成功运行。

### 练习1：理解内核启动中的程序入口操作

阅读 kern/init/entry.S内容代码，结合操作系统内核启动流程，说明指令 la sp, bootstacktop 完成了什么操作，目的是什么？ tail kern_init 完成了什么操作，目的是什么？

####  `la sp, bootstacktop`

- **操作说明**： 
  `la sp, bootstacktop` 是 RISC-V 汇编中的 **“Load Address”** 伪指令，用于将符号 `bootstacktop` 所代表的内存地址加载到栈指针寄存器 `sp` 中。 
  该符号在链接脚本中被定义为内核启动栈（`bootstack`）的**栈顶地址**，即栈空间的最高地址，通常位于 `.data` 段中通过 `.space KSTACKSIZE` 预留的一块静态内存区域的末尾。

- **目的**： 
  内核刚被 OpenSBI 跳转执行时，CPU 的栈指针处于未初始化状态。而后续调用 C 函数（如 `kern_init`）必须依赖有效的栈来保存返回地址、函数参数和局部变量。 
  因此，该指令的核心目的是**为内核初始化阶段建立一个可用的运行时栈**，确保 C 代码能够正常执行。  
  
  > RISC-V 的栈向低地址增长，故 `sp` 必须初始化为栈空间的高地址（即 `bootstacktop`）。

---

####  `tail kern_init` 

- **操作说明**： 
  `tail kern_init` 是 RISC-V 汇编中的**尾调用跳转指令**（等价于 `j kern_init`），它直接将程序计数器（PC）设置为 `kern_init` 函数的入口地址，并**不保存返回地址**（即不修改 `ra` 寄存器）。 
  此时 `kern_init` 是用 C 语言编写的内核主初始化函数，其地址由链接器确定。

- **目的**： 
  将控制权从汇编编写的**内核入口点（`kern_entry`）** 正式移交到**C 语言实现的内核初始化逻辑**，完成从底层引导代码到高级语言运行环境的过渡。
