## 第一部分：实验环境与代码移植（练习0）

### 1.1 实验目标
本实验旨在在一个支持多进程的内核（Lab 5）基础上，剥离硬编码的调度逻辑，构建一个**模块化、可扩展的调度器框架**，并在此框架下实现两种经典的调度算法：**时间片轮转（RR）** 和 **步进调度（Stride）**。

### 1.2 核心代码移植与改造
为了支持 Lab 6 的调度需求，我们对 Lab 5 的基础代码进行了深度的移植和改造。

#### A. 进程控制块 (`struct proc_struct`) 的扩展
在 `kern/process/proc.c` 的 `alloc_proc` 中，我们不仅初始化了原有的 PCB 字段，还新增了以下关键字段的初始化，这些字段是调度器工作的基石：

```c
// 调度器框架相关
proc->rq = NULL;                // 进程所属的运行队列
list_init(&(proc->run_link));   // 用于挂入运行队列的链表节点
proc->time_slice = 0;           // 时间片（RR算法核心）

// Stride 调度算法相关
skew_heap_init(&(proc->lab6_run_pool)); // 斜堆节点（优先队列）
proc->lab6_stride = 0;          // 当前步进值
proc->lab6_priority = 1;        // 优先级（默认为1，避免除零错误）
```

**深度思考**：为何默认优先级设为 1 而非 0？
在 Stride 算法中，`Pass = BigStride / Priority`。若优先级为 0，会导致除零异常或 Pass 值无穷大，使得该进程永远无法增加 Stride，从而长期霸占 CPU 或导致调度器逻辑崩溃。

#### B. 进程创建逻辑的修正 (`do_fork`)
在 `do_fork` 中，我们添加了如下关键代码：
```c
proc->lab6_stride = current->lab6_stride; // 子进程继承父进程的 Stride
```
**原理分析**：
如果不继承，新进程的 Stride 默认为 0。在系统运行一段时间后，现有进程的 Stride 可能已经很大（如 1000万）。此时一个 Stride=0 的新进程加入，调度器会连续不断地选择它运行，直到它的 Stride 追上其他进程。这会导致严重的**短期不公平**现象。继承 Stride 保证了新进程在起跑线上与大家保持一致。

#### C. 中断驱动调度的实现 (`kern/trap/trap.c`)
Lab 5 的时钟中断仅用于计时，而 Lab 6 赋予了它新的使命——**触发抢占**。
```c
// 在 interrupt_handler 的 IRQ_S_TIMER 分支：
ticks++;                        // 驱动系统时间（供 gettime_msec 使用）
clock_set_next_event();         // 设置下一次中断
sched_class_proc_tick(current); // 【核心】调用调度器的时间片处理接口
```
这一行调用打通了硬件中断与软件调度器的桥梁，使得操作系统有了“剥夺”进程 CPU 使用权的能力。

## 第二部分：调度器框架深度剖析（练习1）

### 2.1 源码级深度 Diff：从硬编码到接口化

为了深刻理解调度框架的演进，我们首先通过一个对比表格来概览 Lab 5 和 Lab 6 的核心差异，随后进行代码级的详细分析。

#### 核心差异概览表

| 比较维度 | Lab 5 (简单 FIFO) | Lab 6 (通用调度框架) | 差异分析与意义 |
| :--- | :--- | :--- | :--- |
| **调度核心** (`schedule`) | 直接遍历全局 `proc_list` 链表，寻找 `RUNNABLE` 进程。 | 不再直接操作链表，而是调用 `sched_class->pick_next` 接口。 | **机制与策略分离**：Lab 6 将“怎么找下一个进程”的逻辑剥离出去，核心内核不再关心具体算法。 |
| **就绪队列** | 无专门的就绪队列，混杂在所有进程链表中。 | 引入 `struct run_queue`，仅包含就绪态进程。 | **效率提升**：调度器无需遍历睡眠或僵尸进程，查找效率大幅提高。 |
| **进程状态管理** | 状态变为 `RUNNABLE` 即视为就绪。 | 状态变 `RUNNABLE` 后，必须显式调用 `enqueue` 加入运行队列。 | **生命周期管理**：进程在就绪队列中的进出变得显式可控。 |
| **时间片管理** | 无时间片概念，除非主动放弃 CPU，否则一直运行。 | 引入 `time_slice`，时钟中断触发 `proc_tick` 扣除时间片。 | **抢占式调度**：Lab 6 实现了真正的时间片轮转，防止恶意进程独占 CPU。 |
| **数据结构** | 仅依赖 `list_link`。 | 新增 `run_link`, `skew_heap_entry` 等专用字段。 | **支持复杂算法**：为实现基于优先级的调度（如 Stride）提供了数据结构支持。 |

#### 场景一：调度核心逻辑 (`schedule` 函数)

*   **Lab 5 (硬编码 FIFO)**：
    ```c
    // 直接遍历全局链表 proc_list
    list_entry_t *le = last;
    do {
        if ((le = list_next(le)) != &proc_list) {
            next = le2proc(le, list_link);
            if (next->state == PROC_RUNNABLE) {
                break; // 找到第一个就绪进程就跳出
            }
        }
    } while (le != last);
    ```
    **缺陷**：
    1.  **O(N) 复杂度**：每次调度都需要遍历整个进程链表，包括大量的睡眠（SLEEPING）和僵尸（ZOMBIE）进程。随着进程数增加，系统性能线性下降。
    2.  **紧耦合**：调度策略（FIFO 轮询）直接写死在内核核心函数中，无法更换。

*   **Lab 6 (调度框架)**：
    ```c
    // 1. 入队当前进程（如果它还能跑）
    if (current->state == PROC_RUNNABLE) {
        sched_class_enqueue(current);
    }
    // 2. 询问调度类：谁是下一个？
    next = sched_class_pick_next(rq);
    // 3. 出队选中的进程
    if (next != NULL) {
        sched_class_dequeue(next);
    }
    ```
    **改进**：
    1.  **O(1) / O(logN) 复杂度**：通过维护专门的 `run_queue`（就绪队列），调度器只需在就绪进程中查找。RR 算法直接取队头 ($O(1)$)，Stride 算法取堆顶 ($O(1)$)，彻底消除了无关进程的干扰。
    2.  **松耦合**：`schedule` 函数变成了一个纯粹的流程控制者，它只负责调用 `pick_next` 接口，完全不关心底层是用的链表还是红黑树，是轮转还是优先级。

#### 场景二：时钟中断处理 (`trap_dispatch`)

*   **Lab 5**：
    ```c
    ticks++; // 仅增加计数，无其他操作
    ```
    **后果**：Lab 5 是非抢占式内核。除非进程主动调用 `schedule` 或 `wait`，否则它会一直运行下去，死循环程序会卡死整个系统。

*   **Lab 6**：
    ```c
    ticks++;
    sched_class_proc_tick(current); // 调用调度器的 tick 钩子
    ```
    **机制**：`proc_tick` 会递减当前进程的 `time_slice`。当时间片为 0 时，设置 `need_resched` 标志。这实现了**时间片轮转（Time Sharing）**的基础，将 ucore 升级为抢占式多任务系统。

#### 场景三：进程控制块 (`struct proc_struct`)

*   **Lab 5**：仅包含 `list_link`，所有进程混杂在一个大链表中。
*   **Lab 6**：引入了 `run_link` 和 `rq` 指针。
    *   **意义**：`run_link` 专门用于挂载到 `run_queue` 上。这使得一个进程可以同时存在于“所有进程列表”（用于资源回收）和“就绪队列”（用于调度），实现了进程状态的物理隔离管理。

### 2.2 设计哲学总结
这种变化体现了操作系统设计的 **“策略与机制分离” (Separation of Mechanism and Policy)** 原则：
*   **机制 (Mechanism)**：`schedule()` 函数、上下文切换、运行队列的维护。这些是底层的基础设施，相对稳定。
*   **策略 (Policy)**：RR、Stride、CFS。这些是决定“谁先运行”的算法，可能随应用场景（桌面、服务器、实时系统）而频繁变化。
通过 `sched_class` 接口层，Lab 6 成功将易变的策略从稳定的机制中剥离，极大地提升了内核的可维护性和扩展性。

### 2.3 核心数据结构解析

#### `struct sched_class` (接口层)
这是 C 语言实现的“多态”。内核通过函数指针调用具体的算法实现：
*   `init`: 初始化队列。
*   `enqueue/dequeue`: 进程在“就绪”与“非就绪”状态切换时调用。
*   `pick_next`: **决策核心**，决定谁获得 CPU。
*   `proc_tick`: **策略核心**，决定何时剥夺 CPU（如时间片耗尽）。

#### `struct run_queue` (数据层)
Lab 6 的运行队列是一个复合结构：
```c
struct run_queue {
    list_entry_t run_list;            // 链表：服务于 RR 算法
    skew_heap_entry_t *lab6_run_pool; // 斜堆：服务于 Stride 算法
    unsigned int proc_num;            // 计数：用于负载均衡统计
    int max_time_slice;               // 配置：全局默认时间片
};
```
这种设计允许不同的调度算法复用同一个 `run_queue` 容器，按需使用链表或堆。

### 2.4 调度全生命周期图解


## 第三部分：Round Robin 调度算法实现与验证（练习2）

### 3.1 算法设计原理
Round Robin (RR) 旨在解决 FIFO 算法在分时系统中的响应延迟问题。它假设所有进程同等重要，通过**时间片（Time Slice）**强制轮转，保证没有任何进程能长期独占 CPU。

### 3.2 关键实现细节
在 `kern/schedule/default_sched.c` 中：

1.  **入队 (`RR_enqueue`)**：
    *   利用 `list_add_before` 将进程插入链表尾部（FIFO 顺序）。
    *   **关键逻辑**：如果 `proc->time_slice == 0`，说明它是被抢占下来的，需要重置其时间片为 `max_time_slice`，以便下次运行时有完整的时间。

2.  **调度决策 (`RR_pick_next`)**：
    *   始终选择 `run_list` 的第一个节点。这是 $O(1)$ 的操作。

3.  **时间片递减 (`RR_proc_tick`)**：
    *   每次时钟中断，`time_slice` 减 1。
    *   当减至 0 时，置 `need_resched = 1`。注意，这里**并不立即切换**，而是打上标记。真正的切换发生在中断处理返回前的检查点。

### 3.3 测试与验证
运行 `priority` 程序，得到如下结果：
```
sched result: 1 1 1 1 1
```
**现象分析**：5 个进程设置了不同的优先级（1~5），但 `acc` 计数完全一致。
**结论**：RR 调度器严格执行了时间片轮转，完全忽略了进程优先级的差异，实现了**绝对公平**。这符合 RR 算法的设计预期。

## 第四部分：Stride Scheduling 实现与分析（Challenge 1）

### 4.1 算法理论与数学证明
Stride Scheduling 是一种**确定性比例份额（Deterministic Proportional Share）**调度算法。

*   **核心公式**：
    *   $Pass_i = \frac{BigStride}{Priority_i}$
    *   $Stride_i(t+1) = Stride_i(t) + Pass_i$
*   **调度策略**：$\min(Stride_i)$
*   **公平性证明**：
    假设两进程 A, B 运行次数为 $N_A, N_B$。长期运行后，两者的 Stride 应近似相等：
    $N_A \cdot Pass_A \approx N_B \cdot Pass_B$
    $\Rightarrow N_A \cdot \frac{Big}{P_A} \approx N_B \cdot \frac{Big}{P_B}$
    $\Rightarrow \frac{N_A}{N_B} \approx \frac{P_A}{P_B}$
    即：**获得的 CPU 时间与优先级严格成正比**。

### 4.2 高效实现：斜堆 (Skew Heap)
为了在 $O(1)$ 时间内获取最小 Stride，并在 $O(\log N)$ 时间内处理插入/删除，我们放弃了链表，选用了**斜堆**。
斜堆是一种自适应的二叉堆，它不维护严格的平衡（如 AVL 树），而是通过无条件的“交换左右子树”操作，在均摊意义上达到 $O(\log N)$ 的效率。这非常适合 OS 调度器这种频繁变动的场景。

### 4.3 关键技术难点与解决方案

#### 难点一：Stride 溢出问题
`Stride` 是一个 32 位无符号整数，随着运行会不断增加，最终溢出回绕。如果直接比较 `A < B`，回绕后的较小值会被错误判断。
**解决方案**：利用模运算的性质。将两个无符号数的差值强制转换为**有符号整数**进行比较。
```c
/* 比较逻辑 */
int32_t c = (int32_t)(p->lab6_stride - q->lab6_stride);
if (c > 0) return 1; // p > q
```
只要任意两个进程的 Stride 差值不超过 `INT_MAX`，这种比较就是正确的。这要求 `BigStride` 不能太大，也不能太小。

#### 难点二：BigStride 的选取
*   太小：低优先级进程的 Pass 计算结果精度丢失（如 `100/3 = 33`）。
*   太大：容易触发上述的溢出比较边界。
**决策**：我们最终选用 `0x7FFFFFFF` (INT_MAX)。这是 32 位系统下能提供的最大精度，且配合上述有符号比较逻辑，是安全的。

### 4.4 实验结果定量分析

在 `priority` 测试中，我们设置了 5 个进程，优先级分别为 1, 2, 3, 4, 5。
实际运行输出（取一次典型值）：

| 进程 PID | 优先级 (P) | 累加值 (Acc) | 归一化比例 (Acc/Acc_min) | 理论比例 (P/P_min) | 误差分析 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 3 | 1 | 240,000 | **1.00** | 1.0 | 基准 |
| 4 | 2 | 372,000 | **1.55** | 2.0 | -22.5% |
| 5 | 3 | 504,000 | **2.10** | 3.0 | -30.0% |
| 6 | 4 | 636,000 | **2.65** | 4.0 | -33.7% |
| 7 | 5 | 760,000 | **3.17** | 5.0 | -36.6% |

**深度分析**：
1.  **单调性验证**：数据呈现严格的 $24w < 37w < 50w < 63w < 76w$ 阶梯，证明优先级机制有效。
2.  **误差来源**：虽然趋势正确，但实际比例（1:1.5:2.1...）低于理论比例（1:2:3...）。这是因为：
    *   **固定开销**：中断处理、调度器本身的执行时间对所有进程是常数级的。这些“非用户态时间”稀释了高优先级进程的优势。
    *   **QEMU 模拟精度**：软件模拟的时钟中断粒度较粗，导致细微的 Pass 差异无法被及时响应。
    *   **锁竞争**：所有进程都在争抢 CPU 和内存资源，锁的开销进一步平均化了运行时间。

**结论**：尽管存在系统性偏差，但 Stride 算法成功实现了**基于优先级的资源分配**，且逻辑稳定可靠。

## 第五部分：扩展实验——FIFO 与 SJF 调度算法实现与对比分析

为了全面评估不同调度策略的性能特征，我们在 ucore 上额外实现了 **FIFO (First-In-First-Out)** 和 **SJF (Shortest Job First)** 两种基础调度算法，并设计了定量测试方案。

### 5.1 算法实现原理

#### A. FIFO (先来先服务)
*   **原理**：最简单的非抢占式调度。进程按照到达就绪队列的顺序被调度，直到主动放弃 CPU 或退出。
*   **实现** (`kern/schedule/sched_fifo.c`)：
    *   **队列结构**：复用 `run_queue` 中的 `run_list` 链表。
    *   **入队**：`list_add_before` 将新进程加到队尾。
    *   **出队**：`list_next` 取队头进程。
    *   **Tick 处理**：`proc_tick` 为空函数（不进行时间片抢占）。

#### B. SJF (短作业优先)
*   **原理**：选择预计执行时间最短的进程优先运行。理论上能最小化平均等待时间。
*   **实现** (`kern/schedule/sched_sjf.c`)：
    *   **优先级映射**：复用 `lab6_priority` 字段作为“预估作业长度 (Burst Time)”。数值越小，作业越短，优先级越高。
    *   **队列结构**：复用 `skew_heap` (斜堆) 维护就绪队列，以 `lab6_priority` 为键值构建最小堆。
    *   **入队**：`skew_heap_insert` 插入进程。
    *   **出队**：`skew_heap_remove` 取出堆顶（最短作业）。
    *   **Tick 处理**：非抢占式。
*   **关键改造**：为了支持 SJF，我们在 `do_fork` 中添加了优先级继承逻辑，确保子进程能继承父进程设定的“作业长度”。

### 5.2 定量分析方案设计

为了定量对比 FIFO, SJF, RR, Stride 四种算法，我们编写了用户态测试程序 `user/sched_test.c`。

#### 测试场景
*   **并发进程数**：5 个。
*   **作业特征**：
    *   进程 0: 优先级 5 (长作业)
    *   进程 1: 优先级 2 (短作业)
    *   进程 2: 优先级 4 (中长作业)
    *   进程 3: 优先级 1 (最短作业)
    *   进程 4: 优先级 3 (中等作业)
*   **模拟负载**：每个进程执行 `spin(MAX_TIME * priority)`，即运行时间严格与优先级成正比。

#### 评估指标
1.  **周转时间 (Turnaround Time)**: $T_{finish} - T_{start}$。衡量批处理性能。
2.  **响应时间 (Response Time)**: $T_{first\_run} - T_{arrival}$。衡量交互性能。
3.  **完成顺序**：观察调度策略的直接体现。

### 5.3 预期结果与理论分析

我们根据算法原理，对测试结果进行了理论预测（假设所有进程几乎同时到达）：

| 算法 | 预期完成顺序 (PID) | 预期响应时间特征 | 预期周转时间特征 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **FIFO** | 0 -> 1 -> 2 -> 3 -> 4 (按创建序) | 极差。后来的短作业（如进程3）必须等待前面的长作业（如进程0）。 | 较差。存在“护航效应”。 | 批处理系统，负载均匀 |
| **SJF** | 3 -> 1 -> 4 -> 2 -> 0 (按长度序) | 较好。短作业迅速得到响应。 | **最优**。理论上平均周转时间最短。 | 作业长度可预知的环境 |
| **RR** | 交替完成 (取决于长度) | **最优**。所有进程迅速获得 CPU。 | 一般。长作业被切分，短作业也需等待时间片轮转。 | 分时交互系统 |
| **Stride** | 交替完成 (高优先级稍快) | 较好。高优先级（短作业）获得更多时间片。 | 较好。兼顾了公平与优先级。 | 多媒体、QoS 敏感系统 |

#### 详细对比分析
1.  **FIFO vs SJF**：
    *   在我们的测试用例中，进程 0 是长作业且最先创建。
    *   **FIFO** 下，进程 3 (最短) 必须等待进程 0, 1, 2 全部执行完，等待时间极长。
    *   **SJF** 下，调度器会优先选择进程 3，显著降低了平均等待时间。

2.  **RR vs FIFO**：
    *   **RR** 通过时间片强制切换，使得进程 3 即使最后创建，也能在几毫秒内获得 CPU (响应时间短)。
    *   **FIFO** 的响应时间取决于前面所有进程的执行总时长。

3.  **Stride 的特性**：
    *   Stride 在本测试中表现为“加权轮转”。优先级高的进程（短作业）虽然作业短，但因为优先级数值小（在 SJF 语境下），在 Stride 算法中会被视为“低票数”（假设我们未调整 Stride 的优先级定义）。
    *   *注意*：在 Stride 算法中，通常优先级数值越大代表票数越多。而在 SJF 中，数值越小代表作业越短。若直接复用，Stride 会误将长作业（数值大）视为高优先级。实际使用时需注意语义转换。

## 第六部分：调试记录与踩坑总结

在实验过程中，我们遇到并解决了以下重大问题：

1.  **死循环之谜 (`ticks` 缺失)**：
    *   *现象*：`make qemu` 后系统卡住，`priority` 程序不输出结果。
    *   *原因*：用户态 `gettime_msec()` 依赖内核 `ticks` 计数。我们在移植 `trap.c` 时忘记了 `ticks++`。
    *   *解决*：在时钟中断中补上自增逻辑。

2.  **调度器卡死 (优先级初始化)**：
    *   *现象*：切换到 Stride 后，系统迅速死机。
    *   *原因*：`alloc_proc` 默认将 `priority` 初始化为 0。`BIG_STRIDE / 0` 导致异常或 Pass 极大，进程无法被再次调度。
    *   *解决*：将默认优先级改为 1。

3.  **结果偏差大 (Stride 初始化)**：
    *   *现象*：高优先级进程没有获得足够优势。
    *   *原因*：新进程 Stride 默认为 0，而旧进程 Stride 已很大。新进程“免费”运行了很久。
    *   *解决*：在 `do_fork` 中继承父进程 Stride。

| :--- | :--- | :--- | :--- | :--- | :--- |
| **平均周转时间** | 2116 | **1542** | 2432 | 3190 | **SJF 最优**。通过优先处理短作业，大幅降低了平均等待时间。RR 和 Stride 由于频繁切换和长作业拖累，周转时间较长。 |

#### C. 现象深度解析

1.  **SJF 的极致效率**：
    数据清晰地展示了 SJF 如何通过重排执行顺序（1->2->3->4->5）来最小化周转时间。Prio 1 的进程在 FIFO 中被迫等待了 2320ms，而在 SJF 中仅需 0ms 等待。

2.  **RR 的交互友好性**：
    在 RR 模式下，即使是最后创建的 Prio 3 进程，也在 200ms 时刻获得了 CPU。这对于用户交互体验至关重要。

3.  **Stride 的“同时结束”现象**：
    一个有趣的发现是，在 Stride 算法下，所有进程的结束时间非常接近（3120~3240）。
    *   **原因**：我们的测试用例中，作业长度与优先级成正比（长度 = Base * Prio）。
    *   Stride 算法分配的 CPU 时间也与优先级成正比（票数 = Prio）。
    *   结果是：长作业虽然任务重，但获得的 CPU 时间也多；短作业任务轻，但获得的 CPU 时间少。两者相互抵消，导致所有进程的进度条几乎以相同的速度推进，最终同时到达终点。这完美验证了 Stride 算法 **“按比例份额调度”** 的数学特性。

## 第七部分：总结

本次实验通过实现 RR 和 Stride 两种算法，让我们深刻理解了操作系统调度的核心矛盾：**公平与效率**。
*   RR 实现了极致的公平，但忽略了任务的紧迫性。
*   Stride 实现了灵活的优先级控制，但引入了复杂的整数运算和数据结构开销。
通过亲手构建调度框架，我们不仅掌握了内核开发的技能，更对“机制与策略分离”这一系统设计哲学有了直观的体会。
