## 练习1：分配并初始化一个进程控制块（需要编码）

`alloc_proc` 函数负责为新进程（内核线程）获取一个空白的进程控制块（`struct proc_struct`），并进行基础的初始化。

### 设计实现过程

`alloc_proc` 的实现遵循了“申请-初始化”的模式，确保返回的 `proc_struct` 是一个干净、可用的状态。

1.  **申请内存**：
    调用 `kmalloc(sizeof(struct proc_struct))` 从内核堆中申请一块内存，用于存放 `proc_struct`。如果 `kmalloc` 返回 `NULL`，表示内存不足，函数也返回 `NULL`。

2.  **基础初始化**：
    对申请到的 `proc` 结构体进行全面的初始化，防止后续操作因脏数据而出错。
    - **状态与标识**：
      - `proc->state = PROC_UNINIT;`: 将进程状态设置为“未初始化”，表示它刚刚被创建，尚未分配核心资源。
      - `proc->pid = -1;`: PID 设置为 -1，表示尚未分配有效的进程标识符。
      - `proc->runs = 0;`: 运行次数清零。
      - `proc->parent = NULL;`: 父进程指针暂时置空，后续由 `do_fork` 设置。
    - **内存与上下文**：
      - `proc->kstack = 0;`: 内核栈顶地址清零，等待后续分配。
      - `proc->need_resched = 0;`: 初始不需要调度。
      - `proc->mm = NULL;`: 内存管理结构置空，内核线程共享内核地址空间，不需要独立的 `mm_struct`。
      - `proc->tf = NULL;`: 中断帧指针置空。
      - `proc->pgdir = boot_pgdir;`: **关键**，所有内核线程共享内核页表，因此其页目录指针直接指向内核启动时创建的 `boot_pgdir`。
    - **标志与名称**：
      - `proc->flags = 0;`: 标志位清零。
      - `proc->name[0] = '\0';`: 进程名清空。
    - **链表初始化**：
      - `list_init(&(proc->list_link));`: 初始化用于连接 `proc_list` 的全局进程链表节点。
      - `list_init(&(proc->hash_link));`: 初始化用于连接 `hash_list` 的哈希表链表节点。

```c
// kern/process/proc.c
static struct proc_struct *
alloc_proc(void) {
    struct proc_struct *proc = kmalloc(sizeof(struct proc_struct));
    if (proc != NULL) {
        proc->state = PROC_UNINIT;
        proc->pid = -1;
        proc->runs = 0;
        proc->kstack = 0;
        proc->need_resched = 0;
        proc->parent = NULL;
        proc->mm = NULL;
        memset(&(proc->context), 0, sizeof(struct context));
        proc->tf = NULL;
        proc->pgdir = boot_pgdir;
        proc->flags = 0;
        memset(proc->name, 0, PROC_NAME_LEN);
        list_init(&(proc->list_link));
        list_init(&(proc->hash_link));
    }
    return proc;
}
```

### 问题解答

**问：请说明`proc_struct`中`struct context context`和`struct trapframe *tf`成员变量含义和在本实验中的作用是啥？**

答：这两个成员都用于保存进程的执行现场，但应用在不同的场景，是理解进程切换和中断处理的关键。

1.  **`struct context context`（上下文）**：
    - **含义**：`context` 结构体仅保存了**进程调度和切换时**必须保存的寄存器。在 RISC-V 中，这包括返回地址 `ra`、栈指针 `sp` 以及所有被调用者保存的寄存器 `s0` 到 `s11`。
    - **作用**：它被 `switch_to` 函数（位于 `kern/process/switch.S`）专门使用。当 `schedule()` 决定从进程 A 切换到进程 B 时，`proc_run()` 会调用 `switch_to(&A->context, &B->context)`。`switch_to` 会将当前 CPU 的 `ra, sp, s0-s11` 保存到 A 的 `context` 中，然后从 B 的 `context` 中加载这些寄存器的值到 CPU。这样，执行流就从 `switch_to` 在 A 进程中的调用点，“跳转”到了 `switch_to` 在 B 进程中的返回点。`context` 是实现**协作式调度**的核心数据结构。

2.  **`struct trapframe *tf`（中断帧）**：
    - **含义**：`trapframe` 是一个指向内核栈上特定区域的指针，该区域保存了**发生中断、异常或系统调用时**的**完整** CPU 现场。这包括所有通用寄存器（`gpr`）、`sstatus`（包含特权级和中断使能位）和 `epc`（异常返回地址）。
    - **作用**：
        - **中断处理**：当特权级从用户态切换到内核态时，硬件或 `trapentry.S` 会将所有寄存器保存在内核栈上，形成一个 `trapframe`，`trap.c` 中的处理函数会接收这个 `tf` 指针以访问和修改用户态的现场。
        - **新线程“伪造”启动现场**：在 `do_fork` -> `copy_thread` 中，父进程的 `tf` 会被拷贝到子进程的内核栈顶。**关键在于**，子进程的 `context.ra` 被设置为 `forkret` 的地址。当子进程第一次被 `switch_to` 调度时，它会从 `forkret` 开始执行。`forkret` 会将 `sp` 指向这个 `tf`，然后跳转到 `__trapret`。`__trapret` 会从 `tf` 中恢复所有寄存器，并根据 `tf->epc`（在 `kernel_thread` 中被设置为 `kernel_thread_entry`）和 `tf->status` 返回。这巧妙地让一个新线程的首次运行看起来像是从一次“中断”中返回，从而进入其预设的入口函数。

**总结**：`context` 是**调度器**用于**线程切换**的**部分**上下文，而 `tf` 是**中断/异常处理**和**新线程启动**时使用的**完整**执行现场。

## 练习2：为新创建的内核线程分配资源（需要编码）

`do_fork` 是 ucore 中创建新进程的核心函数。它以当前进程为蓝本，为其创建一个副本。在本次实验中，它被 `kernel_thread` 调用以创建内核线程。

### 设计实现过程

`do_fork` 的实现严格按照进程创建的逻辑步骤进行，并包含了完善的错误处理机制，确保资源在创建失败时能被正确回滚和释放。

1.  **分配进程控制块**：
    调用 `alloc_proc()` 获取一个新的 `proc_struct`。若失败，则返回 `-E_NO_MEM`。

2.  **设置父子关系**：
    将新进程的 `parent` 指针指向当前进程 `current`。

3.  **分配内核栈**：
    调用 `setup_kstack()` 为新进程分配 `KSTACKPAGE`（通常为2）个物理页作为其内核栈。若失败，则释放已分配的 `proc_struct` 并返回 `-E_NO_MEM`。新进程的 `kstack` 成员记录内核栈的栈底（高地址）。

4.  **复制内存管理结构**：
    调用 `copy_mm()`。根据 `clone_flags`，如果设置了 `CLONE_VM`，则与父进程共享同一个 `mm_struct`。对于内核线程，`current->mm` 为 `NULL`，因此 `copy_mm` 实际上什么也不做，这符合内核线程共享内核地址空间的设定。若失败，则回滚已分配的资源。

5.  **复制线程上下文和中断帧**：
    调用 `copy_thread()`，这是设置新线程入口和启动状态的关键。
    - 在新线程的内核栈顶（`proc->kstack + KSTACKSIZE`）留出 `trapframe` 的空间，并将 `proc->tf` 指向它。
    - 将 `kernel_thread` 中构造的临时 `tf` 拷贝到 `proc->tf` 指向的位置。
    - **设置子进程返回值为 0**：`proc->tf->gpr.a0 = 0;`。这是 `fork` 的标准行为，让子进程知道自己是子进程。
    - **设置 `context.ra` 为 `forkret`**：`proc->context.ra = (uintptr_t)forkret;`。这是为了让新线程第一次被调度时，能够正确地通过 `forkret` -> `__trapret` 的路径来恢复 `tf` 中的现场并开始执行。
    - **设置 `context.sp`**：`proc->context.sp = (uintptr_t)(proc->tf);`。`switch_to` 恢复 `sp` 后，栈指针将指向中断帧的起始位置，为 `forkret` 的执行做准备。

6.  **分配 PID 并加入进程列表**：
    调用 `get_pid()` 获取一个唯一的 PID。然后，将新进程加入 `proc_list`（全局双向链表）和 `hash_list`（用于快速通过 PID 查找）。

7.  **唤醒新进程**：
    调用 `wakeup_proc()` 将新进程的状态从 `PROC_UNINIT` 修改为 `PROC_RUNNABLE`，使其可以被调度器选中。

8.  **返回 PID**：
    向调用者返回新创建进程的 PID。

```c
// kern/process/proc.c
int
do_fork(uint32_t clone_flags, uintptr_t stack, struct trapframe *tf) {
    int ret = -E_NO_FREE_PROC;
    struct proc_struct *proc;
    if (nr_process >= MAX_PROCESS) {
        goto fork_out;
    }
    ret = -E_NO_MEM;
    if ((proc = alloc_proc()) == NULL) {
        goto fork_out;
    }

    proc->parent = current;

    if (setup_kstack(proc) != 0) {
        goto bad_fork_cleanup_proc;
    }
    if (copy_mm(clone_flags, proc) != 0) {
        goto bad_fork_cleanup_kstack;
    }
    copy_thread(proc, stack, tf);

    bool intr_flag;
    local_intr_save(intr_flag);
    {
        proc->pid = get_pid();
        hash_proc(proc);
        list_add(&proc_list, &(proc->list_link));
        nr_process++;
    }
    local_intr_restore(intr_flag);

    wakeup_proc(proc);

    ret = proc->pid;
fork_out:
    return ret;

bad_fork_cleanup_kstack:
    put_kstack(proc);
bad_fork_cleanup_proc:
    kfree(proc);
    goto fork_out;
}
```

### 问题解答

**问：请说明 ucore 是否做到给每个新 fork 的线程一个唯一的 id？请说明你的分析和理由。**

答：**是，ucore 做到了为每个活跃进程分配唯一的 PID。**

`get_pid` 函数通过一个静态变量 `last_pid` 来实现 PID 的分配，其机制如下：

1.  **循环递增**：`last_pid` 在 `[1, MAX_PID)` 这个范围内循环递增。每次请求 PID 时，它会尝试使用 `last_pid + 1`。

2.  **冲突检测**：在选定一个候选 PID 后，`get_pid` 会调用 `proc_find(pid)` 遍历 `hash_list`，检查该 PID 是否已经被某个进程（无论处于何种状态，包括 `PROC_ZOMBIE`）占用。

3.  **处理冲突**：
    - 如果候选 PID 未被占用，则分配成功，更新 `last_pid` 并返回。
    - 如果候选 PID 已被占用，`get_pid` 会继续递增 `pid`（并在到达 `MAX_PID` 时回绕到 1），然后再次进行冲突检测。这个过程会一直持续，直到找到一个未被占用的 PID 为止。

4.  **健壮性**：由于 `MAX_PID`（通常很大，如 32768）远大于 `MAX_PROCESS`（最大进程数，如 4096），所以总能保证在活跃进程中找到一个可用的 PID。即使系统中存在大量僵尸进程占用了 PID，只要活跃进程总数不超过 `MAX_PROCESS`，这个循环查找的机制就能确保最终分配一个唯一的 PID。

因此，通过**“循环递增 + 冲突检测”**的策略，`get_pid` 确保了在任何时刻，系统中所有进程（包括僵尸进程）的 PID 都是唯一的。

## 练习3：编写 proc_run 函数（需要编码）

`proc_run` 函数是执行进程切换的“上层”封装。它被调度器 `schedule()` 调用，负责完成从当前进程（`current`）到目标进程（`proc`）的切换准备工作，并最终调用底层的 `switch_to`。

### 设计实现过程

1.  **检查是否需要切换**：
    首先判断 `proc` 是否就是 `current`。如果是，则无需任何操作，直接返回。

2.  **关中断**：
    调用 `local_intr_save(intr_flag)` 宏。该宏会保存当前 `sstatus` 寄存器的状态（尤其是中断使能位 SIE），然后禁用中断。这是至关重要的**原子性**保证，可以防止在切换页表和上下文的敏感过程中，被时钟中断等打断，导致系统状态不一致。

3.  **更新当前进程指针**：
    将全局变量 `current` 指向新的目标进程 `proc`。

4.  **切换地址空间**：
    调用 `lsatp(curennt->pgdir)`。该函数会将 `current->pgdir`（即新进程的页表基地址）加载到 `satp` 寄存器中。CPU 的 MMU 此后将使用新的页表进行地址翻译。对于本次实验的内核线程，`pgdir` 都是 `boot_pgdir`，所以 `satp` 的值不会变，但这个操作为后续实现用户进程（拥有独立地址空间）打下了基础。

5.  **执行上下文切换**：
    调用 `switch_to(&(prev->context), &(current->context))`。`prev` 是保存的旧 `current` 指针。此函数是汇编实现的，它会：
    - 将 CPU 的 callee-saved 寄存器（`ra`, `sp`, `s0-s11`）保存到 `prev->context` 中。
    - 从 `current->context` 中加载新进程的寄存器值到 CPU。
    - `ret` 指令会跳转到新 `context` 中保存的 `ra` 地址。对于一个新创建的线程，这个地址是 `forkret`。

6.  **开中断**：
    `switch_to` 返回后，表示已经切换回原来的进程（在未来的某个时间点）。调用 `local_intr_restore(intr_flag)`，根据之前保存的 `intr_flag` 恢复 `sstatus` 寄存器，如果进入时中断是开启的，这里就会重新开启中断。

```c
// kern/process/proc.c
void
proc_run(struct proc_struct *proc) {
    if (proc != current) {
        bool intr_flag;
        struct proc_struct *prev = current, *next = proc;
        local_intr_save(intr_flag);
        {
            current = proc;
            lsatp(curennt->pgdir);
            switch_to(&(prev->context), &(current->context));
        }
        local_intr_restore(intr_flag);
    }
}
```

### 问题解答

**问：在本实验的执行过程中，创建且运行了几个内核线程？**

答：**创建并运行了 2 个内核线程。**

1.  **`idleproc` (pid 0)**：
    - 在 `proc_init()` 函数中，系统将当前的执行环境“改造”为第一个内核线程，即 `idleproc`。它并没有通过 `do_fork` 创建，而是直接“认领”了 `bootstack` 作为其内核栈，并被赋予 pid 0。它的主函数是 `cpu_idle()`，在没有其他任务时运行。

2.  **`initproc` (pid 1)**：
    - 同样在 `proc_init()` 中，紧接着通过 `kernel_thread(init_main, ...)` 创建了第二个内核线程 `initproc`。
    - `kernel_thread` 调用 `do_fork`，为其分配了新的内核栈和 `proc_struct`，并赋予 pid 1。
    - 它的入口函数是 `init_main`，负责打印 "Hello world!!" 等信息。

**验证**：
`make qemu` 的输出日志清晰地显示了 `initproc` 的创建和执行：

这表明 `idleproc` 在 `cpu_idle` 中调用 `schedule()`，调度器找到了处于 `PROC_RUNNABLE` 状态的 `initproc`，并通过 `proc_run` 成功切换到 `initproc` 执行。因此，整个实验过程中，`idleproc` 和 `initproc` 这两个内核线程都被创建并参与了运行和调度。

## Challenge & 思考题

### 问：说明语句 `local_intr_save(intr_flag); ... local_intr_restore(intr_flag);` 是如何实现开关中断的？

答：这个宏组合并非简单的“开/关”，而是实现了“保存并禁用，事后恢复”的临界区保护机制。

-   `local_intr_save(intr_flag)`:
    1.  它会读取 `sstatus` 寄存器。
    2.  检查 `sstatus` 中的 `SIE` (Supervisor Interrupt Enable) 位，判断当前中断是否处于开启状态。
    3.  将这个状态（`true` 或 `false`）保存到 `intr_flag` 变量中。
    4.  如果中断是开启的，则通过写 `sstatus` 寄存器来清除 `SIE` 位，从而**禁用中断**。如果中断本就是关闭的，则不做任何操作。

-   `local_intr_restore(intr_flag)`:
    1.  它会检查 `intr_flag` 变量的值。
    2.  如果 `intr_flag` 为 `true`（表示进入临界区前中断是开启的），它就会通过写 `sstatus` 寄存器来置位 `SIE`，从而**重新启用中断**。
    3.  如果 `intr_flag` 为 `false`，则什么也不做，保持中断关闭的状态。

**总结**：这种机制确保了临界区代码（如 `proc_run` 中的上下文切换）的原子性，同时又避免了无条件地开启中断，从而正确地维护了嵌套临界区的状态。

### 问：`get_pte()` 函数中有两段形式类似的代码，结合 sv32, sv39, sv48 的异同，解释这两段代码为什么如此相像。

答：这两段相似的代码分别处理 RISC-V 多级页表的第一级页目录和第二级页目录的遍历/创建，它们的相似性源于多级页表结构的**递归/迭代**特性。

-   **共性**：无论是 sv32, sv39, 还是 sv48，它们都遵循一个共同的设计哲学：将虚拟地址分段，每一段作为下一级页表的索引。`get_pte` 的逻辑就是：
    1.  用虚拟地址的高位（`PDX1`）作为索引，在顶级页目录中找到一个页目录项（PDE）。
    2.  **检查该 PDE 是否有效** (`PTE_V`)。如果无效，说明下一级的页表尚不存在。
    3.  如果需要创建 (`create == true`)，则分配一个新物理页，将其地址填入 PDE，并设置有效位等标志。
    4.  使用该 PDE 指向的下一级页表的基地址，结合虚拟地址的次高位（`PDX0`），重复上述过程。

-   **代码相似的原因**：`get_pte` 中的第一段代码处理 `pgdir -> pdep1`（第一级），第二段代码处理 `pdep1 -> pdep0`（第二级）。这两段逻辑完全一样，都是“**索引 -> 检查 -> 创建（如果需要）**”的模式。这种结构上的自相似性，正是多级页表设计的核心。

-   **异同**：sv32/sv39/sv48 的区别主要在于虚拟地址宽度和页表级数不同，导致索引的位数（`PDX1`, `PDX0`, `PTX`）和级数可能不同。但 `get_pte` 的实现巧妙地通过宏（`PDX1`, `PDX0`）抽象了这些差异。只要宏定义正确，同样一套代码逻辑就可以支持不同的分页模式，体现了良好设计的扩展性。

### 问：目前 `get_pte()` 函数将页表项的查找和页表项的分配合并在一个函数里，你认为这种写法好吗？有没有必要把两个功能拆开？

答：这种合并写法在当前 ucore 的规模和场景下是**可以接受的，甚至可以说是简洁高效的**，但也有其缺点。

-   **优点**：
    1.  **接口简单**：调用者只需一个函数就能完成“确保得到一个可用的页表项”的任务，无需关心中间页表是否存在。
    2.  **逻辑集中**：页表遍历和创建的逻辑紧密耦合，都放在一个函数内，便于理解和维护。
    3.  **减少重复代码**：如果拆分，`create_pte` 函数内部仍然需要先 `find_pte`，会有代码重复。

-   **缺点**：
    1.  **功能不纯粹**：一个函数做了两件事（查找和创建），违反了单一职责原则。
    2.  **潜在的副作用**：一个只想“只读”查找的调用者，如果错误地将 `create` 标志设为 `true`，可能会意外地分配内存，改变了页表结构。

-   **是否有必要拆分**：
    -   **在当前实验中，没有必要**。ucore 中对 `get_pte` 的调用场景都很明确：要么是需要映射（`page_insert`），必须创建；要么是查找（`page_remove`），不需要创建。通过 `create` 标志可以清晰地区分这两种意图。
    -   **在更复杂的操作系统中，可能会拆分**。例如，可以提供一个 `walk_pgdir` 或 `find_pte` 函数，它只负责查找，如果页表不存在则返回 `NULL`，绝不分配内存。然后再提供一个 `create_pte_mapping` 之类的函数，内部调用 `walk_pgdir` 并处理分配逻辑。这样可以为只读的内核工具（如内存调试器）提供一个更安全的接口。

**结论**：对于本实验而言，当前 `get_pte` 的设计是实用主义和简洁性的良好平衡，拆分的必要性不大。
